# Redis 与数据库双写一致性保障策略深度解析

在高并发读的场景下，引入 Redis 作为缓存是极其常见的架构设计。然而，当数据发生变更时，如何保证 Redis 缓存与底层数据库（如 MySQL）之间的数据一致性，是一个必须面对的经典问题。

以下是常见的几种双写一致性保障策略的深度解析，包括其工作流程、并发冲突分析、优缺点及适用场景。

---

## 1. 先更新数据库，再更新缓存 (Update DB first, then update Cache)

### 👥 工作流程
1. 写请求到来，先更新数据库（DB）中的数据。
2. 数据库更新成功后，紧接着更新 Redis 缓存中对应的 Value。

### ⚠️ 并发冲突分析（写写并发）
在并发写场景下，可能导致缓存与数据库不一致：
1. 线程 A 更新数据库。
2. 线程 B 更新数据库。
3. 线程 B 更新缓存。
4. 线程 A 更新缓存。

**结果**：数据库中是线程 B 的最新值，而缓存中是线程 A 的旧值。由于缓存被旧值覆盖，产生了长期脏数据。

### ⚖️ 优缺点
* **优点**：缓存一直有值，后续的读请求可以直接命中缓存，不会发生缓存穿透。
* **缺点**：
  * 高并发写场景下极易产生脏数据。
  * 性能浪费：如果写多读少，或者缓存的计算逻辑复杂（例如需要多表关联计算生成一个 JSON），每次更新 DB 都去计算并更新缓存，会产生不必要的性能开销。

### 🎯 适用场景
极少使用。仅适用于并发极低、且缓存 Key 计算简单且极易发生读请求的场景。

## 2. 先更新缓存，再更新数据库 (Update Cache first, then update DB)

### 👥 工作流程
1. 写请求到来，先更新 Redis 缓存。
2. 缓存更新成功后，再更新数据库。

### ⚠️ 并发冲突分析（写写并发）
与第一种策略类似，并发写入时：
1. 线程 A 更新缓存。
2. 线程 B 更新缓存。
3. 线程 B 更新数据库。
4. 线程 A 更新数据库。

**结果**：缓存中是 B 的最新值，但数据库中是 A 的旧值。当缓存失效后，系统读取数据库的旧值并写入缓存，导致长期的脏数据。此外，如果第二步更新数据库失败，但缓存已更新，回滚极难处理。

### ⚖️ 优缺点
* **优点**：无明显优点。
* **缺点**：不仅存在并发不一致的风险，而且一旦数据库更新失败，缓存难以实现回滚，极易造成数据混乱。

### 🎯 适用场景
**强烈不推荐**在生产环境使用。

---

## 3. 先删除缓存，再更新数据库 (Delete Cache first, then update DB)

### 👥 工作流程
1. 写请求到来，先将对应的 Redis 缓存 Key 删除。
2. 缓存删除成功后，再去更新数据库。

### ⚠️ 并发冲突分析（读写并发）
这是该策略最核心的问题，在高并发读写下极易发生：
1. 线程 A 进行写操作，先**删除缓存**。
2. 线程 B 进行读操作，发现**缓存未命中（Cache Miss）**。
3. 线程 B **读取数据库**，拿到旧值。
4. 线程 B 将旧值**写入缓存**。
5. 线程 A **更新数据库**为新值。

**结果**：数据库中是新值，缓存中是旧值，导致后续所有读请求都拿到脏数据。

### 💡 优化方案：延时双删 (Cache Delay Double Delete)
为了解决上述并发问题，引入延时双删机制：
1. 先删除缓存。
2. 更新数据库。
3. 睡眠一段时间（如 100ms ~ 500ms，具体取决于读业务的平均响应时间和主从同步延迟）。
4. 再次删除缓存（将线程 B 写入的旧缓存删掉）。

* **延时双删的缺点**：
  * 延迟时间难以精确预估。如果延迟时间过短，读请求可能还没完成旧值写入；如果延迟时间过长，会降低写接口的吞吐量（通常需异步删除以避免阻塞写线程，进而增加了代码复杂度）。

### ⚖️ 优缺点
* **优点**：逻辑较简单，避免了写写并发时的缓存计算浪费。
* **缺点**：在读写并发高的场景下，不加延时双删会产生脏数据；加上延时双删会增加系统延迟和复杂度。

### 🎯 适用场景
适用于读写并发不高，且对一致性要求一般的辅助业务。

## 4. 先更新数据库，再删除缓存 (Update DB first, then delete Cache) —— Cache Aside Pattern

### 👥 工作流程
这是最经典的 **Cache Aside（旁路缓存）** 模式的写策略：
1. 写请求到来，先更新数据库。
2. 数据库更新成功后，直接删除对应的缓存 Key。

### ⚠️ 并发冲突分析（理论上的读写并发）
理论上存在极其罕见的并发不一致场景（需要缓存恰好失效）：
1. 线程 A 读数据，缓存失效，从 DB 读取旧值。
2. 线程 B 写数据，更新 DB。
3. 线程 B 删除缓存。
4. 线程 A 将第 1 步读到的旧值写入缓存。

**为什么实际极难发生？**
因为步骤 3（删除缓存）必须在步骤 4（写入缓存）之前发生。而写数据库（步骤 2）的耗时通常远大于读数据库和写缓存（步骤 1 和 4）。因此，线程 A 几乎总是会在线程 B 删完缓存前就把数据写入缓存了。

### 🛠️ 删除缓存失败的兜底方案
如果第二步“删除缓存”由于网络闪断等原因失败，依然会导致不一致。常见兜底手段有：
1. **设置过期时间（TTL）**：为所有缓存 Key 设置合理的过期时间（如 1 小时），确保即使发生失败，系统也能在一定时间内达到最终一致性。
2. **引入消息队列重试**：将删除失败的 Key 发送到 MQ，由消费者订阅并重试删除，直到成功。

### ⚖️ 优缺点
* **优点**：
  * 极大降低了并发冲突的概率。
  * 每次写操作只需删除缓存，无需复杂的缓存计算，性能开销小。
  * 实现简单，是目前业界最推崇的最佳实践。
* **缺点**：存在极小的一致性缝隙（如删除缓存失败的短暂时间内，或者极端并发下）。

### 🎯 适用场景
绝大多数互联网高并发业务的首选方案（如商品信息、用户信息、文章内容等）。

## 5. 异步监听 Binlog 删除缓存 (Asynchronous Binlog Replication)

### 👥 工作流程
1. 写请求到来，仅负责更新数据库，更新成功后直接返回响应。
2. 部署一个专门的数据库同步组件（如阿里巴巴开源的 Canal），将自己伪装成数据库的 Slave，实时订阅并解析数据库的 Binlog（归档日志）。
3. 监听到指定表的写操作（Insert/Update/Delete）后，解析出变更的 Key，并发送到消息队列（MQ）。
4. 缓存更新服务消费 MQ 消息，异步执行 Redis 缓存的删除或更新操作。

### ⚖️ 优缺点
* **优点**：
  * **应用层解耦**：业务代码只需要对 DB 进行操作，无需在业务逻辑中嵌入任何缓存操作，符合单一职责原则。
  * **高可用与可靠性**：利用 MQ 的 ACK 机制和重试机制，可以几乎 100% 保证缓存删除成功。
  * **性能好**：写请求更新完 DB 即可直接返回，缓存删除完全异步进行。
* **缺点**：
  * 架构复杂度大幅增加，引入了 Canal、MQ 等中间件，增加了系统的运维与开发成本。
  * 属于最终一致性方案，中间件同步存在一定延迟，在极短时间内读请求仍可能拿到旧数据。

### 🎯 适用场景
大型分布式系统、超高并发系统，且对缓存更新时效性要求为最终一致性、需要极致解耦和可靠性的核心链路（如电商平台商品状态同步等）。

## 6. 强一致性保障：分布式锁 / 读写锁 (Distributed Lock / ReadWriteLock)

在某些极其特殊的业务中，必须要求数据**强一致性**（即只要数据库更新了，接下来的读请求绝对不能读到旧值）。

### 👥 工作流程
1. 引入分布式锁（如基于 Redisson 的 `RReadWriteLock`）。
2. **读操作**：获取**共享锁（读锁 Lock）**。允许多个读请求并发执行，但如果此时有写锁，读请求会被阻塞。
3. **写操作**：获取**排他锁（写锁 Lock）**。只允许一个写请求执行，同时会阻塞所有的读请求和写请求。
4. 写请求在锁保护内更新 DB 并更新/删除缓存。

### ⚖️ 优缺点
* **优点**：完全杜绝了任何并发一致性问题，实现了强一致性。
* **缺点**：锁机制将原本的并发读写串行化，大大降低了系统的吞吐量，甚至可能让缓存失去提高系统并发性能的意义。

### 🎯 适用场景
并发量不算极高，但对一致性要求极其严苛的金融类、交易类及订单状态相关的核心场景。

---

## 总结建议

在实际系统设计中，没有绝对完美的方案，只有最契合业务的妥协。一般而言：

* **首选方案**：**先更新数据库，再删除缓存 + 缓存过期时间（TTL）兜底**（即 Cache Aside）。
* **高可用解耦方案**：**先更新数据库，通过 Canal 异步订阅 Binlog 删除缓存 + MQ 重试**。
* **强一致性方案**：使用 **分布式读写锁（RReadWriteLock）**，但在非必要情况下应尽量避免，因为其性能损耗非常大。
